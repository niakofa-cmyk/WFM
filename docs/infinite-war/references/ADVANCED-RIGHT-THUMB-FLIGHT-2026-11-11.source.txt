
### WFM — Advanced right-thumb flight controls and aerial maneuvering

I investigated the updated `niakofa-cmyk/WFM` repository, particularly the Orbital flight simulation, mobile joystick implementation, maneuver recognition, combat physics, and multiplayer control boundaries.

My conclusion is that we should substantially upgrade the right-thumb controller and make it a second, fully capable flight-maneuvering surface.

Your proposed design is a good direction. I would go beyond simply adding four directional buttons. We should develop a responsive, analog, multidirectional maneuver controller that allows pilots to move their spacecraft in three-dimensional space while maintaining combat control.

There is already enough foundation in the Orbital engine to implement this without creating a separate flight engine.

### 2\. The new two-thumb control architecture

I recommend retaining the two-thumb layout, but giving the right thumb substantially more capability.

The revised responsibilities:

* Left thumb: primary propulsion, forward/reverse throttle and coordinated flight steering.

* Right thumb: pitch, aim, lateral movement, vertical movement and directional evasive maneuvers.

* Dedicated combat actions: fire, missiles, target lock and countermeasures.

* Boost: directional boost gesture, with its own energy and cooldown rules.

The most important enhancement is that right-thumb movement should affect the spacecraft itself, not just the camera or aiming direction.

### How the boost should work

I would not implement this as an ordinary button press that temporarily increases forward speed.

Instead, introduce a dedicated directional maneuver intent.

For example:

* The pilot double-taps right.

* The gesture recognizer identifies the right-direction burst.

* The input system sends a versioned maneuver request.

* The Orbital simulation checks energy, cooldown and ship eligibility.

* The simulation applies a short directional acceleration burst.

* The ship physically moves right with an appropriate thruster animation.

* The maneuver enters cooldown.

This should also work for diagonals.

Important: A directional boost should not make a ship invulnerable. Missiles must still be capable of tracking it, and bullets must still be capable of hitting it.

We want skilled pilots to evade attacks through timing and positioning, not become impossible to damage.

### 5\. The most important engineering change: upgrade the shared Orbital simulation

The good news is that the underlying physics already supports the majority of the movement we need.

In `lib/orbital-sim/src/flight.ts`, `integrateSpatialFlight()` already calculates:

* Quaternion orientation.

* Pitch, yaw and roll.

* Forward propulsion.

* Lateral thrust.

* Vertical thrust.

* Three-dimensional velocity.

* Momentum and stabilization.

* Boost acceleration.

* Energy consumption.

* Speed limits.

* Obstacle and boundary collisions.

This means we should not create a second movement system inside `Arena.tsx`.

We should extend the shared engine's existing input and simulation contracts.

### Proposed new control mapping

| Right-thumb input | Orientation          | Translation              |
| ----------------- | -------------------- | ------------------------ |
| Up                | Pitch upward         | Vertical thrust upward   |
| Down              | Pitch downward       | Vertical thrust downward |
| Left              | Turn left            | Lateral thrust left      |
| Right             | Turn right           | Lateral thrust right     |
| Upper-left        | Combined orientation | Up and left              |
| Upper-right       | Combined orientation | Up and right             |
| Lower-left        | Combined orientation | Down and left            |
| Lower-right       | Combined orientation | Down and right           |

This is the hybrid approach I recommend: the right thumb controls both the aircraft's attitude and its vector movement, with separately adjustable gains.

That preserves manual aiming while adding physical movement. It also gives us a more expressive flight model than simply converting the right stick into a second movement joystick.

We should introduce a control-profile setting so pilots can retain the existing aim-only behavior if they prefer it.

The critical requirement is that browser simulation, server simulation and replay processing all understand the same control intent.

We should not use client-side timers to determine the duration or success of an online boost. The server must own maneuver activation, duration, cooldown and energy consumption.

The existing local `pulseVectorManeuver()` uses browser timers. That is acceptable as a starting point for offline input experimentation, but it should not become the authority for competitive or persistent multiplayer maneuvers.

### 7\. Multiplayer and Orbital integration safeguards

There is an important limitation in the repository that we must address before promoting these controls.

The shared `pilot-controls.ts` contract already understands the flight axes, but the current sector adapter deliberately strips local tactical maneuver intents.

The existing barrel-roll gesture is also restricted to the offline Orbital pilot path.

Therefore, the new directional boost must be integrated into the server-authoritative simulation rather than simply made visible in the client.

I recommend:

* Extend the versioned tactical maneuver contract with directional vector boosts.

* Introduce server-owned energy, cooldown and maneuver duration.

* Update deterministic browser/server simulation parity.

* Increment the Orbital rules version from its current version 5.

* Preserve existing historical replay compatibility.

* Keep old control profiles functional.

* Introduce the new profile in an isolated test environment.

* Verify multiplayer synchronization before competitive deployment.

Do not enable the new maneuver protocol in existing live matches until both clients and servers negotiate the same simulation version.

* No guaranteed missile immunity.

### My final design recommendation

I would make this a defining characteristic of the WFM flight experience.

We should not settle for a conventional mobile flight joystick with a few additional buttons.

We should create a Dual-Thumb Dynamic Flight and Combat Maneuver System.

The left thumb controls propulsion and coordinated steering. The right thumb controls attitude and multidirectional movement, including rapid evasive maneuvers and directional boosting.

The spacecraft should respond physically, retain momentum, bank and rotate convincingly, and remain controllable while the pilot fires weapons and evades enemy attacks.

Most importantly, the controls should be consistent across the Orbital Combat Lab, training, campaign operations and eventually the persistent Infinite War universe.

I recommend implementing Phase 1 through Phase 3 together as the first isolated development package, then testing it in the Combat Lab before migrating it into authenticated multiplayer.

That gives us a meaningful improvement in flight capability without destabilizing the existing engine or competitive combat.

* Implement persistent spatial sessions

    Replace process-local ownership with shared session coordination and authoritative simulation leases.

* Implement durable checkpoints

### How the rear-positioning AI should work

This is particularly important.

The AI should not simply aim at the player's current position. It should attempt to establish a position from which it can attack effectively.

For example:

![Pursuit Tradition / Ritual in STBC | World Anvil](https://images.openai.com/static-rsc-4/zJeqACyoxgBjBO4ITkaTgn0JDc-kO71JDywDKjQ407n-bjR_Tb-0SI5RyopdFtq3AKPpem62rlcMigXYoViaNsdea6fiZH16sVYDkLvjB2CMvl0k839JaW1ErmGYEWk7QUEmGtN7hwHqMWAG5le71MvuJxmZ6yrs8JJzhsLBHDDiC_4tU02Svw9MKuaTWRSk?purpose=fullsize)

Imagine the player is flying forward.

The enemy AI should:

* Estimate the player's current forward vector.

* Predict the player's future position.

* Select a rear-quarter interception point.

* Calculate the velocity needed to reach that point.

* Adjust its heading and lateral thrust.

* Match the player's speed where appropriate.

* Acquire a firing solution.

* Fire guns or launch a missile.

* Reposition if the player performs an evasive maneuver.

It should continually recalculate instead of following a fixed waypoint.

A useful tactical calculation is:

P_{\\text{intercept}} =
P_{\\text{player}} +
V_{\\text{player}}t +
D_{\\text{rear}}

Where:

* is the player's position.

* is the player's velocity.

* is the estimated interception time.

* is the desired rear-quarter offset.

We should use a dynamically selected offset rather than always placing the enemy directly behind the player's ship. Otherwise, the AI becomes predictable.

### Enemy AI behavioral states

I recommend a state machine:

```mermaid

stateDiagram-v2
    [*] --> Patrol
    Patrol --> Detect: Player detected
    Detect --> Intercept: Threat confirmed
    Intercept --> Pursue: Close distance
    Pursue --> RearPosition: Seek firing angle
    RearPosition --> Attack: Firing solution
    Attack --> Pursue: Target changes heading
    Attack --> Evade: Incoming threat
    Pursue --> Evade: Missile warning
    RearPosition --> Flank: Wingman available
    Flank --> Attack: Coordinated firing solution
    Evade --> Reposition: Threat avoided
    Reposition --> Pursue: Reacquire target
    Attack --> Retreat: Hull critical
    Retreat --> Regroup: Safe distance
    Regroup --> Pursue: Re-engagement
```

The AI must also understand when it is losing a fight. A badly damaged fighter should not behave like a fully equipped interceptor.

### 3\. Make enemy AI genuinely capable of evading the player's attacks

We should give enemy pilots the same fundamental flight capabilities that we give human pilots.

That means using the shared Orbital flight simulation, not creating an artificial movement animation.

For example, if the player fires a missile:

* AI detects the incoming missile.

* AI evaluates its estimated time to impact.

* AI calculates whether a lateral dodge, vertical climb, dive or barrel roll is appropriate.

* AI checks its maneuver energy and cooldown.

* AI executes the maneuver through the actual flight physics.

* AI attempts to reacquire its offensive position.

The AI should not dodge every attack perfectly.

We need varying intelligence levels:

| Enemy class | Behavior                                                       |
| ----------- | -------------------------------------------------------------- |
| Rookie      | Basic pursuit, occasional evasion                              |
| Regular     | Attempts rear positioning and missile dodging                  |
| Veteran     | Flanking, predictive interception and coordinated attacks      |
| Elite       | Combines maneuvers, countermeasures and intelligent weapons    |
| Ace         | Adapts to repeated player tactics and coordinates with wingmen |

An Ace should be challenging because it makes better tactical decisions, not because it receives unfair speed or damage bonuses.

### 4\. Introduce energy restoration for every confirmed kill

I recommend implementing this

I particularly like your idea of restoring energy when a player destroys an enemy.

It creates an important combat loop:

Attack → maneuver → expend energy → destroy target → recover energy → continue fighting.

It also encourages skilled pilots to stay engaged rather than constantly retreating to recharge.

However, I would introduce a controlled reward system rather than automatically restoring every energy resource to 100%.
