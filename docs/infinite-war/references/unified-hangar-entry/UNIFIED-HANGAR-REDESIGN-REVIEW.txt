My findings
There are already foundations that we should preserve:
- A title and main-menu sequence.
- An existing HANGAR navigation state.
- Faction and ship selection.
- Ship refitting and technology upgrades.
- Online 5v5 room creation and joining.
- A separate persistent GalaxyScreen.
- Campaign progression and station travel.
- Server-backed player progression and rewards.
However, the architecture still separates these experiences.

The existing HomeScreen.tsx presents campaign deployment, arcade, armory, and settings as separate menu choices. Persistent Galaxy is another separate entry. Multiplayer has its own room-creation interface.

The menu.ts state machine also routes campaign and arcade through HANGAR, while other functions follow different navigation paths.

That is the architectural problem we should solve.

We should not throw away these systems. We should bring them together under a unified hangar experience.
Important distinction
The repository's persistent galaxy is not yet the fully realized shared multiplayer universe.

The existing travel documentation explicitly describes six campaign locations as single-player account progression, not a shared multiplayer galaxy.

That distinction matters. We should build the new interface around the intended infinite universe without pretending all of its systems are already operational.

The most important technical requirement
The new hangar must not create a second game engine.

It should use the same underlying rendering, simulation, world state and asset systems as the rest of the game.

I also noticed an important architectural discrepancy: the repository documentation still describes a deferred Three.js combat engine, including its own approximately 486 KB chunk. I did not find evidence in the inspected main-branch source establishing the complete Orbital Engine integration you have described.

We need to reconcile that before implementing the new environment.

The Orbital Engine should remain the rendering and simulation authority if that is the established master-engine decision. We should not introduce a competing Three.js hangar or universe renderer.

7. Recommended implementation sequence
I would proceed in six controlled stages.
1. Stage 1 — Unified game shell
   
   Consolidate boot, authentication, title, home and hangar into one coherent player-entry lifecycle. Remove competing primary entry points.
2. Stage 2 — 3D military hangar
   
   Implement the persistent environment, ship presentation, pilot, fleet background, lighting, animations and vertical UI.
3. Stage 3 — Integrated military systems
   
   Connect shipyard, fleet management, loadouts, weapons, upgrades, campaign, multiplayer and communications.
4. Stage 4 — Exclusive universe gateway
   
   Connect the single entry action to the existing universe services and evolve the galaxy interface into the actual persistent navigation environment.
5. Stage 5 — Continuous world transitions
   
   Implement hangar-to-universe, universe-to-station, station-to-operation and operation-to-combat transitions. Preserve player state and progression.
6. Stage 6 — Verification
   
   Test portrait and landscape layouts, mobile performance, ship rendering, navigation, multiplayer connections, world persistence and recovery.
Acceptance criteria
The redesign should not be considered complete until:
- There is one primary player entry experience.
- The hangar is the persistent home environment.
- Every major military system is accessible without leaving the hangar shell.
- There is one exclusive universe gateway.
- All universe destinations are accessed through the universe environment.
- The hangar and universe use the established Orbital Engine.
- Existing campaign, multiplayer, ships, rewards and account progression continue to function.
- The entire experience is responsive on Android and iOS.
- No placeholder buttons or simulated world functionality are represented as operational features.
