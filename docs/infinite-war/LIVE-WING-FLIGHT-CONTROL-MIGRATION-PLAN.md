# Live Wing Flight-Control Migration Plan

## Decision

Do not change the live 5v5 Wing control mapping in this step. The validated Wing
path remains on its current server contract until a versioned replacement has
client/server parity and replay evidence. This plan describes the migration
gates; it does not enable a new control mode, change rewards, or authorize a
Production rollout.

## Current boundary

- The mobile vector-thrust stick currently feeds the server-run sector
  simulation, whose input contract includes bounded `strafe` and `vertical`
  axes and whose snapshots are generated by the server.
- Live Wing still sends its established `throttle`, `yaw`, `strafe`, `pitch`,
  `fire`, `ult`, `lock`, `evade`, and `preset` frame to the server.
- Wing runs on the deterministic, planar match simulation. The sector
  simulation is six-axis 3D flight. These are distinct simulation contracts;
  mapping one stick directly into the other without a server-side design would
  change steering, aiming, collision, and outcome behavior.
- Wing matchmaking, authentication, disconnect handling, results, and
  progression/reward settlement remain server-owned and are outside this
  control migration.

## Staged migration

### 1. Freeze the live baseline

- Keep the current Wing input mapping and packet shape unchanged.
- Capture representative, versioned Wing replays and their per-tick state
  checksums before modifying shared simulation behavior.
- Record current server validation, 30 Hz tick behavior, reconnect handling,
  input-rate limits, competitive queue gates, and reward eligibility tests.
- Treat the 5v5 server simulation—not local prediction—as the authority for
  movement, weapons, damage, match outcomes, and settlement.

### 2. Define a versioned control and simulation contract

- Specify a new control profile and simulation/rules version before adding any
  new axes to a live packet. Negotiate the version when joining a match; do not
  infer it from client-provided fields.
- Keep old clients on the old contract. Reject extra, missing, out-of-range, or
  non-finite values for each negotiated version.
- Decide explicitly how pitch, yaw, coordinated bank, vertical thrust, boost,
  brake, and drift behave in Wing's competitive space. Do not silently reinterpret
  existing `strafe`, `evade`, or aim inputs.
- Keep the server authoritative. Client prediction may improve responsiveness,
  but the server validates inputs and supplies corrections; clients never submit
  positions, damage, objective completion, match results, or rewards.
- If the new profile uses the shared orbital simulation, port the server
  simulation and replay format together. Do not run different physics on the
  client and server or adjudicate a new mode with the old planar simulation.

### 3. Build parity evidence without changing live matches

- Add deterministic fixtures for keyboard, gamepad, and touch inputs, including
  neutral release, reconnect, malformed frames, and simultaneous flight/combat
  actions.
- Require the same pinned replay checksums at every frame in Node and Chromium.
  Re-pin gameplay checksums only after the determinism gate passes.
- Test bounded axes, sequence numbers, stale input, packet-rate limits, and
  server snapshot correction. Include network impairment and ten-client
  convergence tests using a shared authoritative tick.
- Verify private rooms and AI-fill remain no-reward, and verify competitive
  queue eligibility and server settlement remain unchanged.
- Run mobile tests in landscape, then separately request physical-device
  verification. Browser emulation is not phone certification.

### 4. Stage behind an isolated opt-in gate

- Exercise the new profile only in the isolated staging environment and a
  separate, explicitly enabled test queue. Leave Production configuration,
  database, and deployment untouched.
- Never mix control/simulation versions inside one active match. Assign the
  version at match creation and keep it fixed for the full match and replay.
- Keep reward settlement disabled for new-profile test matches until positive,
  eligible staging settlement and idempotency evidence passes independently.
- Require a full 10-human competitive test for 5v5 queue behavior; simulated
  clients and two-pilot cooperative sector tests do not certify that gate.

### 5. Promote or roll back deliberately

- Promote only after the contract, deterministic replay, multiplayer,
  progression, security-boundary, and physical-device gates are reviewed.
- Roll back by disabling new-match assignment to the new version. Let a match
  finish on its pinned version or interrupt it under the existing no-reward
  shutdown policy; never hot-swap controls or physics mid-match.
- A failed or interrupted test must not mutate saved profiles, credits,
  inventory, campaign progression, or completed rewards.

## Completion criteria

The live migration is not ready until all of the following are demonstrated:

1. Existing Wing clients and matches continue to use the old contract.
2. New controls have an explicit, server-validated, negotiated version.
3. Server and browser replays match frame by frame in the supported runtimes.
4. Ten authenticated humans complete the staging 5v5 flow with stable shared
   snapshots through latency and reconnect tests.
5. Existing matchmaking and reward safeguards pass unchanged, plus a separate
   controlled staging settlement verifies idempotency.
6. Physical landscape-device checks pass for aim, flight, fire, lock, release,
   pause, reconnect, and accessibility/readability.
7. A tested match-boundary rollback leaves player progression and the reward
   ledger unchanged.

Until then, the safe action is to keep the new left-stick behavior in the
server-run sector/Orbital paths and preserve the proven live Wing mapping.
