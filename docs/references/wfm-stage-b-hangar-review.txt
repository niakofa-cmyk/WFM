2. How well have the recommendations been implemented?
A. Orbital combat foundation
Substantial progress
The PR has done several things correctly:
- Added lib/orbital-sim as a shared rules package.
- Added quaternion-based spatial flight, thrust, inertial movement and braking.
- Added target-specific missile acquisition and guided missiles.
- Added armor absorption and spatial projectile collision.
- Added a separate offline Combat Lab.
- Added a server-side orbital authority harness.
- Preserved the existing live socket and authentication protocol.
The strongest decision is that the new simulation is shared between the client and the server-side test harness. This reduces the risk of the client and server gradually implementing different combat rules.

The deterministic math work is also valuable. The six replay comparisons passing is a good regression signal.
B. The new server authority
Foundation only — not live multiplayer
The new orbital-authority.ts is a useful simulation harness. It owns ten synthetic pilot seats, fixed ticks, input validation, ammunition, cooldowns, projectiles, damage and destruction.

But the source explicitly says it is not registered with the existing socket service.

That means:
- The ten seats are test fixtures, not ten authenticated humans.
- There is no live orbital matchmaking.
- The orbital snapshots are not being distributed to connected players.
- There is no live orbital reconnect or match settlement.
- There are no validated competitive orbital rewards.
This is the correct way to begin the authority implementation. It would be unsafe to describe it as completed 5v5 multiplayer.

3. Errors and risks I would address
I did not find evidence of a failing workspace workflow in the current PR. I did find several issues that need attention before this becomes the canonical runtime.
Finding	Why it matters	Recommendation
Combat Lab remains offline	New combat is not yet part of real operations	Keep it as a training entry temporarily, then connect through a coordinated server integration
Old command menu remains	Player journey is fragmented	Replace the command list with Hangar, Universe and Operations navigation
3D flight is not the same as complete 6DoF combat	New spatial simulation is still isolated from live Wing	Integrate flight, collision, damage and targeting as one versioned combat contract
Authority harness has synthetic seats	Not evidence of real ten-player play	Bind authenticated sessions and test real staging players
Orbital balance is provisional	The Lab uses stronger pilot damage tuning and provisional missile damage	Establish a separate competitive balance profile before ranked play
Mobile performance is unverified	Successful builds do not establish sustained 60 FPS	Test frame time, memory, thermal behavior and touch response on real Android and iOS devices

A specific technical issue to investigate
The shared orbital flight rules currently use a simplified boundary and collision model. The flight integrator constrains craft to a radius of 78 simulation units and resolves obstacle contacts using spherical rock collision.

That is acceptable for an initial bounded combat sector, but it is not yet a complete universe-flight model. We need sector boundaries, travel transitions, collision behavior and environmental forces to become explicit simulation rules.

I would also add tests for:
- Zero-distance and near-zero-distance target geometry.
- Two or more simultaneous missile impacts.
- Dead or destroyed target handling.
- Stale input and target changes during acquisition.
- Repeated or delayed input packets.
- Simultaneous ship destruction and match resolution.
- Snapshot size and simulation cost at maximum sector population.
These are recommendations for additional coverage, not claims that the existing tests have failed.

The images above are visual references, not approved WFM ship designs. The actual hangar should use the WFM ship roster, faction identities and approved assets.
The live switching mechanic is especially important
When the player selects another ship, the actual 3D model in the hangar should change.

It should not simply change the displayed ship name.

The selection should:
1. Transition the currently displayed hull out of the presentation position.
2. Load or activate the selected ship's actual 3D model.
3. Animate it into the display position.
4. Update its faction markings, propulsion, weapon mounts and lighting.
5. Update its real ship statistics and available loadout.
6. Allow the player to rotate and inspect the model.
7. Save the selected ship through the existing account/loadout system when confirmed.
The model and its gameplay identity must come from the same canonical ship definition. This prevents the hangar from showing a ship with statistics or equipment that do not match the actual combat simulation.

We should reuse and improve the existing SHIPS, ROSTER and procedural ship-visual systems rather than invent a separate hangar roster.

6. How I would implement Stage B
I would divide Stage B into five development deliverables.
Stage	Implementation	Acceptance proof
B1	Unified onboarding and account entry	New and returning players reach the correct hangar
B2	3D hangar environment	Live 3D ship displayed in the hangar
B3	Interactive hull selection	Switching ships changes actual model and stats
B4	Hangar operations interface	Loadout, upgrades, faction and mission selection work
B5	Connected deployment loop	Hangar → briefing → sector → combat → debrief → hangar

B1 — Build the unified entry experience
Replace the existing collection of command cards with a proper entry and onboarding flow.

Preserve Clerk and existing account services. Do not create another authentication mechanism.
B2 — Build the actual 3D hangar
Create a reusable Three.js hangar scene.

Use:
- A central ship display platform.
- A large hangar interior with open space and depth.
- Animated hangar lighting.
- Visible repair and maintenance activity.
- A view of Mars or the surrounding orbital environment.
- A controlled camera system.
- Performance-aware lighting, shadows and model detail.
The hangar should work on mobile as well as desktop. It must not require a high-end desktop GPU just to open the main game screen.
B3 — Connect ship selection
Use the existing ship roster and gameplay statistics.

Every selectable ship should have:
- A real 3D model.
- Faction and ship-class identity.
- Correct movement characteristics.
- Shield, armor and hull statistics.
- Weapon compatibility.
- Upgrade availability.
- Actual selection and persistence behavior.
B4 — Make the hangar the central operations hub
The player should access the rest of the game through contextual interfaces:
- Hangar: ships, loadouts and technology.
- Operations: campaign and cooperative missions.
- Universe: star systems, sectors and travel.
- Warfront: competitive faction warfare.
- Squadron: friends, team and multiplayer activities.
- Pilot Profile: achievements, records and progression.
The player should not need to return to the old command menu to move between these systems.
B5 — Prove the entire loop
The first complete Stage B demonstration should be:

Sign in → Hangar → Select USSF fighter → Change weapon loadout → Select Rust Disc operation → Launch into orbital combat → Destroy target → Complete objective → Debrief → Return to hangar.

The same player identity and saved loadout must survive the journey.

This is the point where we can say the player is entering a cohesive game rather than opening separate prototypes.

8. Final recommendation
I would make the hangar the first major visual milestone of Infinite War.

The orbital combat work is giving us a stronger combat foundation. Stage A has established the audit and architectural direction. Stage B should now give the player a reason to feel that they have entered a real universe.

The hangar is where the player identifies with their faction, sees their ship, makes meaningful decisions, prepares for the next operation and returns after battle.

My recommended order is: Stage B hangar and player journey first, then the connected mission loop, then the live multiplayer orbital integration.

I would keep PR #11 open as the technical foundation, get the reported Stage A documents into the repository, and implement Stage B as a separate, reviewable continuation. No production deployment or destructive restructuring is needed to start this work.
